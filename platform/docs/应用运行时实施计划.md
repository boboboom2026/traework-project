# 应用运行时（薄应用托管层）实施计划

> 以 CrewAI 为底座、以流程编排 Flows 为业务支撑，实现「一套平台支撑各类应用」，首个应用为点餐系统。
> 原则：不做"市场形态"应用中心；做"薄应用运行时"（应用注册表 + 统一入口 + 租户隔离 + 能力网关）。

## 目标架构

```
┌────────────────────────────────────────────────────┐
│          企业 AI 协作办公平台（CrewAI 底座）          │
│  多智能体协作 / 编排(Planning/并行) / 知识 RAG / 记忆 │
│  流程编排 Flows（事件驱动 + 条件分支）                │
│  审批门 Approval / 工具库 / LLM 提供商              │
├────────────────────────────────────────────────────┤
│           应用运行时层（本次实施）                    │
│  应用注册表 manifest → 统一入口 /app/{app}/{tenant}  │
│  租户模型 + 每租户独立数据域 (app_store)             │
│  能力网关 /api/app-gateway  + 前端 AppSDK           │
├────────────────────────────────────────────────────┤
│  应用示例：点餐系统（用户端 H5 + 商家端 H5，Flow 承载业务）│
└────────────────────────────────────────────────────┘
```

## 阶段 0 · 应用注册表（manifest）

- 文件：`backend/app_runtime.py`
  - AppManifest：`app_id / name / version / description / entry(url) / endpoints[] / capabilities[] / crew_ref / flow_ref / data_models[] / approval_required[]`
  - 加载器：启动时扫描 `backend/apps/manifests/*.json`，校验（必填、id 唯一、capability 存在），失败不阻断启动
- API：`GET /api/apps`（列表，含能力/端/编排/流程绑定）；注册以 manifest 配置为准（删除/禁用文件即下架）
- 前端：新增「应用管理」入口与页面（应用列表 + 访问链接）
- 应用：`apps/manifests/menu-ordering.json`（点餐应用声明）
- 验收：`GET /api/apps` 返回已注册应用；非法 manifest 加载时不阻断

## 阶段 1 · 统一入口与路由

- `main.py`：`GET /app/{app_id}/{tenant_id}` 分发（static 托管 / remote iframe），未注册 404
- 静态资源：应用 manifest entry 指向托管目录或外部地址
- 鉴权：用户端游客可浏览；商家端需身份（阶段 3 PIN）
- 验收：直开 URL 到达对应端；未注册 404

## 阶段 2 · 租户模型与数据域（硬骨头，不拖后）

- `platform_store`：新增 `tenants` 集合（tenant_id/name/status/apps[] 订阅表）+ CRUD；停用即入口失效
- 新增 `backend/app_store.py`：每租户独立 `DataDomain(f"{app_id}@{tenant_id}", data/apps)`，强制显式 `(app_id, tenant_id)`；提供 list/get/create/update/delete
- 审批记录统一带 `app_id/tenant_id`；平台审批页可查归属
- 验收：两个租户并发使用同一应用，数据与审批互不可见

## 阶段 3 · 能力网关与 SDK

- 新增 `backend/app_gateway.py`：路由前缀 `/api/app-gateway/{app_id}/{tenant_id}/...`
  - 身份上下文注入：role(customer/merchant/admin)；商家签发需 PIN（环境变量 `APP_MERCHANT_PIN`，默认 `123456`）
  - `runFlow`：转发现有 Flows 引擎推进步骤（业务支撑主路径）
  - `runCrew`：转发现有编排引擎（现有 run 链路），注入租户上下文
  - `approvals`：提交/决策（复用审批门，记录带租户归属）
  - `data`：`app_store` 域 CRUD（merchant/admin 可写）
- 前端 SDK：`backend/public/apps/sdk.js`（getContext / invoke / runFlow / runCrew / approvals / data；无上下文优雅降级）
- 验收：任意 H5 应用引入 SDK 可拿身份、推进 Flow、触发审批闭环

## 阶段 4 · 点餐应用租户化接入（Flows 为业务支撑）

- 改造 `apps/hosted/menu_ordering`：按租户实例化数据域（store 接受 tenant 路径）
- 点餐业务 Flow（平台 flows 集合）：`智能推荐 →（顾客确认）→ 下单 → 审批 → 出餐通知`
- 用户端 / 商家端 H5 改走 SDK（菜单/订单/审批走租户域）
- 种子演示租户「示例餐厅」
- 验收：商家维护菜品；顾客"智能推荐 → 下单 → 审批通过 → 订单可见/出餐"全流程

## 阶段 5 · 市场化管理（后置不启动）

触发条件：出现第三方开发者 / 应用数量爆炸（几十个起）/ 客户自助开通。任一出现再补浏览页、上架审核、版本发布。

## 关键约束

1. 阶段 2 数据域隔离先行，接口定型前单独评审
2. 网关严禁重建编排：runFlow/runCrew 一律转发现有引擎，只注入租户上下文
3. 应用接入三步：manifest → H5 页面 → SDK（不碰平台代码）
